# lauren v0.1

安装和 Skill 入口见 [../README.md](../README.md)。宿主路径见 [接入.md](接入.md)。

这一版把讨论里的六阶段做成一个不用 LLM 的 CLI。下面是当前程序的行为。讨论记录里更早的待讨论项，若这里已经选了做法，只表示程序现在这么做。

## 项目配置和单次 policy

`lauren.project.json` 只放多次流程共用的内容：

- `environments`：允许的环境。示例用 `development`、`integration`、`staging`、`production`。
- `defaults`：新建流程时拷贝的 `environment`、`release_stage`（`included` 或 `excluded`）、`artifact_level`（`standard` 或 `abbreviated`）、`integration_branch`。集成分支由项目自己写，程序不写死 `main`。`check_timeout_seconds` 是单项检查的项目默认超时，不拷进单次 policy。
- `checks` 和 `requirements`：共享目录。

检查用 `gate`：`self_verification`、`acceptance`、`release`。层次是 `static`、`unit`、`integration`、`interaction`、`release_readback`。可选的 `environments` 声明这份证据可以在哪些环境取得。`argv` 仍是会被执行的显式信任命令。每项检查可以用 `timeout_seconds` 覆盖项目默认超时。`require_executed` 为 true 时，输出里必须有 `lauren-stats executed=<非零> skipped=<数>`，否则即使退出码是 0 也记失败。没有这个字段的旧检查不受影响。

语言适配器放在仓库的 `adapters/`，不是内置命令。Go 的在 `adapters/go-test/`，它跑 `go test -json`，自己打印 `lauren-stats`。全部跳过、没有匹配到测试、或只有包级别的 pass，都是 `executed=0`。父测试只包着子测试时，不把父测试的 pass 再算一次；父测试自己 fail 仍算执行了一次。`lauren init --adapter go-test` 会把这份适配器复制到项目的 `.lauren/adapters/go-test/`，并加上一条 `require_executed: true` 的检查，argv 指向复制后的副本。非 Go 项目可以自己写任何程序，只要在输出里打一行 `lauren-stats executed=<n> skipped=<m>`，真实失败用非零退出码，再在检查上打开 `require_executed`。找不到适配器时，设置 `LAUREN_ADAPTERS` 指向含有适配器目录的那一层。

创建变更时把 `defaults` 拷成该变更的 `policy`，命令行可以覆盖。之后的门禁看这份记录，不回读项目默认值。`change policy set` 必须带理由，并写入历史。同时把当时的 checks 冻成这次变更自己的计划，并把当时生效的超时写进计划。之后再改 `lauren.project.json` 里的检查或超时，不会改这份计划，也不会因此作废这次已经记下的证据。必过检查不能拿掉。可选检查可以用 `change create --skip 名称=理由` 排除，理由会留在计划里。未授权的命令不能加进来。

明确需求阶段还可以 `change plan skip` 或 `change plan include`。过了这一步，agent 不能直接改计划。要先 `change plan propose`，状态里会出现 `plan_pending`。只有所有者执行 `change plan confirm --owner-confirmed` 才生效，并作废受影响的证据。agent 不得自己加上 `--owner-confirmed`。没有计划字段的旧变更仍按项目里的 checks 跑；新建的变更都会冻结。

- 改 `environment` 或 `release_stage` 会让当前的接受和发布声明失效，不会把另一个环境里仍然有效的检查一起作废。
- 改 `artifact_level` 会按新规则重核已提交产物。精简记录只要求需求和方案里的目标与做法，但不取消必过检查和独立验收。
- 改 `integration_branch` 或改成 `integration_intent=not_in_current_iteration` 只影响这次流程。还没合入时，开发和验收证据不必作废。已经合入且未 `change integration withdraw` 时，拒绝修改并说明必须先撤回。撤回不会自动改 git。
- `not_in_current_iteration` 表示暂不纳入当前迭代，不是空字符串。在新目标成为项目当前集成分支之前，不能占用共享预发或生产的发布读回。

默认值只影响之后新建的流程。指纹绑定源码候选，以及 `checks` / `requirements`。检查超时也算进这份目录哈希：用的是生效后的 `defaults.check_timeout_seconds`，再加上每个检查自己的 `timeout_seconds`。改其中任一都会作废已有检查证据。其他 defaults 不进指纹。`.lauren/runtime/`、`.lauren/problems/` 和 `.lauren/project/` 也不算。git 忽略的文件不在 `git status` 里，只改它们不会让源码候选过期。

候选指纹使用 `fingerprint v2`。已提交文件来自 `git ls-tree -z`，工作区变化来自 `git status --porcelain=v1 -z`。路径按 NUL 分隔，不按 shell 引号或换行切分。重命名或复制时，当前路径在前，原路径在后。普通文件哈希内容；符号链接哈希链接文本，不跟随目标。文件不存在记为删除。其他读取错误，包括路径不再是普通文件，使指纹成为 `unknown`，不能把检查记为通过。v2 的哈希和以前按行解析的结果不同，所以升级前留下的通过记录不会被当成仍然有效。比较工作区路径时会做规范化，`/tmp` 与 `/private/tmp` 这种别名不会被当成两个根。

## 工作区与共享配置

当前 Worktree、配置正文和 runtime 是三件事。候选指纹、检查的 cwd、变更、锁和 `.lauren/runtime/` 都属于当前 Worktree。不能把主工作区的代码当成这个 Worktree 的候选，也不能几个 Worktree 共用一份 runtime。

配置正文可以仍放在工作区根的 `lauren.project.json`，也可以只放一份在主检出的 `.lauren/project/lauren.project.json`。发现顺序是：

1. `--root` 只表示从哪个目录开始找，可以是工作区里的子目录。先确定当前 git worktree，不越过这个仓库去读祖先仓库的配置。
2. 工作区根的 `lauren.project.json` 若是软链接，或只含 `schema` 和 `shared_config` 的引用，就载入它指向的正文。目标可以是文件，也可以是含有 `lauren.project.json` 的目录。相对路径相对当前 Worktree。引用断了、目标不存在，或目标在当前 Git 仓库之外，就报错，不改去自动发现另一份。
3. 引用里再写 `checks` 或其他字段会被拒绝。没有 Worktree 级覆盖，也不做 extends 深合并。环境和集成分支的差别仍用这次变更的 policy。
4. 没有本地入口时，若当前检出，或能定位到的主检出，有 `.lauren/project/lauren.project.json`，就用这一份。`config_mode` 为 `shared`，并且没有 `entry`。主检出来自 `git worktree list` 的第一项，而且它必须真是工作区。不把 git common dir 的父目录当成主工作区。
5. separate git-dir 如果列不出主检出，自动发现失败，诊断是「无法定位主工作区」，这时要自己写 `shared_config`。主检出自己目录里的共享配置仍然找得到。
6. 根上的完整配置和 `.lauren/project/lauren.project.json` 同时存在，报「配置冲突」，不静默选一份。
7. 只有根上的完整配置时，`config_mode` 是 `legacy`。别的 Worktree 不会因此把主工作区当成自己的运行根；那份文件若没有进该 Worktree 的检出，就仍是未初始化。不在 git 里的旧项目仍会从子目录向上找到这份文件，但不会越过带 `.git` 的目录。
8. 什么都没有，报「未初始化」。配置在工作区根之下的子目录时，会写出找到的路径，并说明它不在 worktree 根。主工作区还有 `.lauren/`、但共享文件不见了，会写出主工作区路径，并说明没有 `.lauren/project/lauren.project.json`，而不是当成从来没初始化。

`status` 的 `workspace` 给出 `worktree`、`runtime`、`config_path`、`config_mode`（`legacy`、`shared`、`symlink`、`reference`）、`main_worktree`、`resource_dir`。软链接和引用还会给 `entry`。旧字段保持不变。

新的链接工作区在 `git worktree add` 之后执行 `lauren init-worktree`（路径可省略，默认当前工作区；也可以写在命令后面）。它只在该工作区建立入口：根上的 `lauren.project.json` 是指向共享正文的软链接，Skill 与插件清单也是指向 `.lauren/project/` 里那一份的软链接。不复制 runtime、变更或证据，也不创建变更。入口里不写 checks。已有的普通文件或已跟踪的接入文件不会被覆盖或隐藏，提示人工迁移。断链仍报「配置入口断了」。没有共享配置时，诊断与发现规则相同。

重复执行不会再添一份入口或排除规则。`--preview` 只列出要改的路径。`--undo` 只删这个 Worktree 的受管软链接。`info/exclude` 在 git 公共目录里，所有 Worktree 共用；里面的规则都带前导 `/`，只匹配工作区根，不隐藏子目录里的同名文件。只要还有别的 Worktree 留着接入记录，撤销就不会删掉这块排除，避免把别人的入口变成未跟踪文件。最后一个接入撤销后才去掉区块。不改项目 `.gitignore`，也不使用 skip-worktree。自带 Skill 打进二进制，不依赖从 lauren 源码目录执行。`.lauren/init.json` 只说明接入了哪些路径，不是测试通过或开发完成。

```bash
git worktree add ../feature -b feature
lauren init-worktree ../feature
lauren --root ../feature status
lauren --root ../feature skills check
```

共享配置里的 checks 或超时变了：之后新建的变更冻住新计划；已经创建的变更保持原来的计划。过了明确需求，仍然要 `change plan propose`，再由所有者 `change plan confirm --owner-confirmed`。`.lauren/project/` 不计入候选指纹，所以只改共享配置不会把在途通过记成候选过期。检查命令仍在当前 Worktree 里执行，路径里不能带 `..`。共享脚本写成 `resource:` 开头的路径，相对 `.lauren/project/` 解析，不用 shell。脚本还会拿到 `LAUREN_WORKTREE` 和 `LAUREN_RESOURCE` 两个环境变量，不要靠脚本自己的文件位置推断业务根。旧的相对路径和绝对路径保持原样。只有命令名、需要从 PATH 找的程序不做内容摘要，状态里会写明未覆盖。

`resources` 列出这次检查额外绑定的文件，同样可以是 `resource:` 或工作区相对路径。程序记下这些文件的字节和软链接目标，摘要不进候选指纹。字节变了、链接目标变了、文件没了，旧通过就失效。执行过程中这些文件变了，这次不能记成通过。没声明的文件，包括共享 Skill 文案，不会把别的检查一起作废。已经冻住的计划不会因为共享配置里改了 argv 就换命令。

`skills check` 只说明本机入口文件读得到。这不表示宿主已经把这段上下文注入了会话。

## 单项检查超时

单位是整数秒。没有命令行临时覆盖。

优先级是：检查上的 `timeout_seconds`，然后 `defaults.check_timeout_seconds`，然后内置 600 秒。缺字段或写成 0 都表示沿用上一级。负数，以及大到 `time.Duration` 无法表示的秒数，读取配置时直接拒绝。字符串、小数和布尔值无法解析成整数秒。

```json
{
  "defaults": {
    "check_timeout_seconds": 600
  },
  "checks": [
    {
      "name": "unit",
      "layer": "unit",
      "gate": "self_verification",
      "argv": ["./checks/unit.sh"],
      "required": true,
      "timeout_seconds": 900
    }
  ]
}
```

上面的 `unit` 用 900 秒。没有 `timeout_seconds` 的检查用项目默认；项目默认再缺省就是 600 秒。以前单项检查硬编码 120 秒，这个限制已经换成现在的配置。旧结论不会因为程序换了默认值就被当成仍然有效。

每次实际执行的检查都会在 JSON 的 `timeout_seconds` 和证据日志开头的 `timeout_seconds=` 里记下这次生效的秒数。到点记为失败，不记为通过。超时后杀掉这次检查启动的进程组，并限制等待输出管道关闭的时间，避免子进程留下后把检查挂住。

## 状态放在哪

每个变更一个目录：`.lauren/runtime/changes/<id>/`，里面是状态、证据和锁。`.lauren/runtime/worktree.json` 指向这个工作区正在做的变更。这些都 gitignore，不写进 git 目录。

同一个工作区同时只能有一个 `active` 或 `blocked` 的变更。另一个 git worktree 可以各自再有一个，状态不共用。共享的 staging/production 发布读回同时只能被一条流程占用；其他流程可以继续开发和验收。

## 阶段怎么走

名称仍是：明确需求、制定方案、实现与自验、验收与交付、发布与观察、复盘与改进。

`defaults.red_gate` 缺省是 `required`。字段省略和写成 `required` 是同一件事：离开实现与自验之前，要有同一次变更、同一项检查上的先失败再通过。失败那次的输出里要有脚本自己写的 `lauren-class classification=assertion_fail` 或 `behavior_fail`。程序不根据退出码猜测分类。每次检查都会记下日志的 sha256，字段是 `log_digest`。分类只在脚本写了合法的 `lauren-class` 行时才有。

已经存在、而且配置里没有这个字段的项目也会变成 required。下一次离开实现与自验时，如果还没有上述记录，推进会被拒绝。要回到以前可以只靠通过离开实现的行为，必须在 `lauren.project.json` 里显式写 `defaults.red_gate: "off"`。`init` 会把 `required` 写进新文件。进行中的变更也读这份项目配置，不把开关冻进当时的 policy。

可以 `change red skip --reason "..."` 显式跳过这一次变更。理由会出现在 `status` 的 `red.skip_reason` 里，不能静默跳过。没写 `--reason` 会被拒绝。跳过只作用于这一次变更，不会把项目默认改回 off。

`examples/shelf` 不写 `red_gate`，所以走缺省的 required。演示脚本会先用 `.lauren/runtime/red-replay` 让 `unit` 打出 `behavior_fail` 并失败，再删掉这个标记跑真正的通过。标记在被 gitignore 的 runtime 里，不改变候选指纹。这是在默认打开的门禁下补上一次 Red，不是把示例改成 off。

自验失败就留在实现与自验，改候选后重跑。验收失败会记下问题并回到实现与自验，不能把验收改成通过。发布读回失败同样记下问题并回到实现与自验；不自动部署，也不自动撤回部署，共享环境要等人处理，然后 `change release clear`。

门禁对每一项检查、每一个被接受的环境，只看仍适用于当前候选（发布读回则是当前集成版本）的最新一条结果。同一环境里后来的失败、partial、blocked 或超时会盖过更早的通过。另一个环境或另一项检查的结果不会互相覆盖。候选或 checks/requirements/超时变了，不再适用的记录失效。`status`、`next` 和 `change advance` 用的是这一条规则。

`release_stage=excluded` 的流程验收之后直接复盘，不需要发布读回。`included` 时，进入发布与观察之前要先 `change integration record` 记下合入的分支和 SHA。离开这一阶段还要至少一项必过检查同时满足 `gate=release` 和 `layer=release_readback`，并且它的最新结果是通过、环境被接受、绑定的就是这次集成 SHA。没有这样的检查、还没跑、失败、过期、环境不对或版本不对，都不能进入复盘。`gate=release` 但层次不是 `release_readback` 的检查仍然按必过项执行，但不能代替机器读回。发布声明本身不使 `release_verified` 为 true。

发布读回绑这个集成版本，不绑未合入的工作区。`release_readback` 只承认检查声明的环境；没声明时只承认 `staging` 和 `production`。开发环境里打印的版本不能充当已部署证据。已经在用、并且启用了发布阶段的项目，需要补上上述必过读回；只排除发布阶段的项目不用改。

## QA 报告

需要把报告内容绑进门禁时，在 requirement 上写 `requires_report: true`。没有这个字段的旧项目行为不变。

报告默认放在 `.lauren/reports/`。`defaults.reports_dir` 可以改成 `.lauren/` 下的另一个相对目录，不能指到 `runtime` 或 `problems`。这个目录不计入候选指纹，避免报告自己把候选弄脏。

`change report submit --requirement <id> --file <路径> --source self|declared|external` 把当时的 sha256、候选指纹、环境和来源种类记到这次变更上。摘要由程序读取文件计算，不能手填。来源只是声明，`source_verified` 恒为 false，不会因为写成 `external` 就变成已验证。

门禁重新计算文件摘要。摘要不一致、文件缺失、候选变了，或环境不被对应检查接受，这条要求就不能算满足。

## 公共问题库

问题不挂在单次变更上。一条问题一个文件，目录是 `.lauren/problems/`，纳入 git。`.lauren/runtime/` 仍然忽略。问题文件也不计入源码指纹，避免记一条记忆就被当成代码变了。

第六步用 `change problem add` 检索公共库。同类的规则是把 title、layer、symptom 去掉首尾空白并收成单空格后完全相同。同类就追加一次 occurrence 并把 count 加一；否则新建。`verified_fixed` 不能在记录时手填。

`defaults.promote_threshold` 默认是 2。只出现一次就留在问题库里，处置写成 `later` 也可以结束这次复盘。次数达到阈值只表示应当晋升：必须把 `target-check` 指到项目里已经存在、而且层次不低于问题层次的检查，程序只给它补一条 requirement，不生成永远失败的占位脚本，也不改写项目自己的 `environments`。还没登记成功时，`later` 不能结束复盘；明确 `rejected` 可以。登记成功的状态是 `promoted`，这时 `verified_fixed` 仍是 false。

`change problem verify` 只有在同一检查先失败、后有仍然有效的通过时，才把 `verified_fixed` 写成 true。新的一次出现会清掉上一次的处置和已验证结论，这一轮要重新处置。验收或发布失败自动记入问题库时先不晋升；到了复盘，若次数已够且写了合法的 `target-check`，推进复盘前会再尝试登记。本轮出现过、还没有 disposition 的问题，以及还留在变更运行时里、没处置的旧问题记录，都不能关闭复盘。晋升会改 requirements，因此作废相关旧证据。

升级程序时只替换二进制。`lauren.project.json`、`.lauren/problems/` 和 `.lauren/runtime/` 留在项目里。

## 状态里的事实

`product_verified` 仍然表示：已配置的 required requirements 都有仍有效的通过。它和新增的 `requirements_met` 是同一个值，留给已经在读这个字段的调用方。它不是独立验收。

另外几个字段把依据分开：

- `self_checks_met`：必过的自验检查都已通过。没有必过自验时是 false。
- `acceptance_checks_met`：必过的验收检查都已通过。没有必过验收检查时是 false。
- `independent_acceptance`：至少有一条 required 且 `independent` 的 requirement，并且这些要求都已满足。自验要求不算。
- `acceptance_source`：当前候选上交付接受记录里的来源字符串，只是声明。
- `source_verified`：这一版恒为 false。CLI 不验证 human、other-session 或 external 的身份，也不会因为来源写成 external 就当成已验证。
- `delivery_accepted`、`release_declared`、`release_verified` 仍然分开。发布声明不是机器读回。
